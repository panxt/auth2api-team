# auth2api 路线图(Roadmap)

本文档记录 `auth2api-team`(fork)在当前版本(v2.2.0,自适应加权并发负载均衡)之后的功能规划方向。仅为方向性规划,具体设计与优先级以实际排期为准。

> 文档定位:团队共享的功能方向备忘;当前架构见 [`ARCHITECTURE.md`](ARCHITECTURE.md),运维见 [`OPERATIONS.md`](OPERATIONS.md)。

---

## 演进路径概览

auth2api 正从「**能用的共享网关**」(v2.2.0:并发负载均衡 + 日志分类 + 容量告警)演进为「**企业级 AI 接入平台**」。规划项收敛到 **5 条主线 + 2 个横切件**:

| | 主线 | 目标 | 归属条目 |
|---|---|---|---|
| 1 | 供给与可靠性 | 接得了更多模型、扛得住更多场景 | ① ② ③ ⑩ ⑰ ⑱ |
| 2 | 成本与 FinOps | 要么真省、要么看得见省 | ⑪ ⑥ ⑬ |
| 3 | 多租户与自助 | 从管理员手工管 → 项目化、自助化 | ⑧ ⑤ ⑭ |
| 4 | 安全 / 合规 / 内容管控 | 对外、合规场景的准入门槛 | ⑦ ⑫ ⑨ |
| 5 | 可观测与质量 | 看得清、可优化、可回归 | ④ ⑮ ⑯ |

> 编号(1–18)为**稳定 ID**,非优先级顺序;推进顺序见文末「推进建议」。

---

## 横切件(优先,使能多条主线)

### 8. 项目 / 分组维度 + 项目级能力开关(底座)

在现有 per-key 治理(配额 / 模型白名单 / 限流 / tier)之上,抽出一层**「项目 / 分组」维度**:能力与配额按项目配置、key 继承。

- **为什么是底座**:语义缓存(⑨)、Guardrails(⑫)、加密(⑦)、分层预算(⑬)都需要**按项目差异化开关**——例如编程项目关语义缓存、问答项目开;对外项目开加密、内网项目开明文审计。⑧ 一次性提供这个差异化配置的承载层。
- **复用点**:现有 `ApiKeyEntry` 的配额 / 白名单 / 限流 / tier 字段与三层配置合并机制,自然延伸到项目层级。
- **注意**:项目 → key 的配置继承与覆盖关系要明确;UI 需要项目管理视图。

### 4. 周期性用量分析 + 飞书通知(通知 / 报表出口)

增加**按天 / 周 / 月 / 年**的使用情况分析,并接入**飞书(Lark)通知**:定期把用量、成本、异常情况汇总推送到飞书群 / 机器人。它同时是**告警与报表的统一出口**——⑥ 的省钱周报、⑬ 的预算告警、容量告警都从这条管道推送。

- **分析侧**(服务于主线 5):在现有统计(`stats/recorder` 已有 `dayFacts` 保留约 120 天 + 当天/当月/全部/自定义区间)基础上,扩展日 / 周 / 月 / 年的聚合维度与对比(环比 / 同比)。
- **通知侧**(横切通道):接入飞书自定义机器人 / webhook,定时推送周期报表;可配置推送频率、内容范围、阈值告警(如成本超预算、错误率升高、账号额度将尽)。
- **注意**:这会引入一个新的**对外出站端点**(飞书 webhook)——需走配置开关、默认可关、内容脱敏(不外发原始 key / 完整对话),与现有"无外部 egress"的安全基线保持一致(见安全审计结论)。

## 主线 1 · 供给与可靠性

### 1. 各平台 API 兜底(fallback)

接入各平台的**官方 API key 通道**作为兜底:当 OAuth 订阅账号访问异常(限流 / 冷却 / 账号池全部不可用)时,自动切换到官方 API 调用,保证服务可用性。

- **定位**:作为账号池调度失败后的**最后一层 fallback**,而非替代账号池——优先用订阅账号(成本优势),仅在订阅侧不可用时才兜到按量计费的 API。
- **衔接现状**:与 v2.2.0 的账号池调度 / 容量告警体系对接——当 `capacitySummary` 判定账号池饱和或全挂时,由 API 兜底兜住请求,而不是直接对客户端返回 429。
- **复用点**:现有 provider registry 与 failover 抽象。

### 2. 支持国内各类模型 + 自部署模型

扩展现有 provider 体系(当前:anthropic / codex / cursor),纳入更多模型来源:

- **国内主流模型**:如通义千问、智谱 GLM、DeepSeek 等。
- **自部署 / 私有模型**:本地 vLLM、Ollama 等 OpenAI 兼容端点。
- **复用点**:多数目标具备 OpenAI 兼容接口,优先复用现有翻译层与 provider 注册机制,新增 provider 适配而非另起炉灶。

### 3. 多模态支持

在转发 / 翻译层(`translator` / `responses-translator`)支持**多模态输入**(图像等),不再局限于纯文本。

- **范围**:请求侧的图像 / 文件等多模态内容透传与协议翻译;跨 provider 的多模态能力差异需做能力探测或降级处理。

### 10. 熔断器 + 会话亲和

把现有 cooldown 升级为正式的**健康感知路由**,并按会话粘账号以保 prompt 缓存。

- **熔断器**:账号连续失败自动熔断、半开探测恢复(circuit breaking),比单纯 cooldown 更稳;与现有 `capacitySummary` / failover 协同。
- **会话亲和**:按 `x-claude-code-session-id` 等会话标识粘住同一账号,进一步提升上游 prompt 缓存命中(本条原在 v2.2.0 并发方案中列为「增强未做」)。
- **复用点**:现有调度器打分函数与 in-flight 账户机制。

### 17. 水平扩展 / 高可用

从当前**单进程 + 本地 sqlite** 演进为多实例 + 共享存储,消除单点。

- **衔接现状**:承接 v2.2.0 并发分析中识别的「单进程瓶颈」隐患。
- **范围**:多实例间共享账号池状态 / 用量 / 配置;健康与就绪探针;sqlite 备份与恢复策略;k8s 友好。

### 18. 批量 API 代理(限兜底通道 + 非交互场景)

对**非实时**请求走 Anthropic Batches 端点,官方再省 50%。

- **原理**:批量提交、不承诺实时(队列错峰算力,≤24h),用延迟换 5 折。
- **重要边界(修正)**:这个折扣是**按量 API key 计费**维度的,**订阅 OAuth 主路径不涉及 token 计费、也基本不开放 Batches**。因此本条**仅适用于第 ① 条「API 兜底通道」中真用官方 API key 的部分**,且仅对非交互流量(离线代码扫描、批量 eval、定时分析)有意义。**不是订阅省钱主线**。

## 主线 2 · 成本与 FinOps

> 前置:`usage/pricing.ts` 价格需先校准到现价(Opus 4.8 现为 $5/$25,旧表写的是 $15/$75 的老 Opus 价),否则 ⑥⑬ 的成本估算偏高约 3 倍。官方价出处:[API 定价](https://platform.claude.com/docs/en/about-claude/pricing)、[订阅定价](https://claude.com/pricing)。

### 11. 智能模型选择(按复杂度路由)

按任务复杂度自动选模型:简单任务走 Haiku / Sonnet,难任务才用 Opus。

- **价值**:订阅场景下**真正省 5 小时窗口额度**(省的是配额,不是 token 费),与 ⑥ 的「看得见的省」互为执行面与展示面。
- **复用点**:现有 provider / 模型解析与调度链路;可结合请求特征或显式标记决策。

### 6. 按 token 使用量展示预估节省费用

在统计 / 看板页,基于实际 token 使用量,自动展示「用共享订阅 vs 走官方 API 按量计费」**预估节省了多少费用**(节省额 + 节省率)。把成本对比从一次性测算变成产品内的实时指标,直观体现号池价值。

- **算法**:预估节省 = Σ(各模型 token 用量 × 官方 API 列表单价,区分 input / output / 缓存读写) − 订阅成本(账号月费之和,需可配置)。
- **复用点**:现有 `stats/recorder` 的 token 用量统计 + `usage/pricing.ts` 定价表。
- **注意 / 前置**:见本主线开头的价格校准;官方订阅按滚动窗口限流、不公开精确 token 配额,节省额是**估算值**,UI 应标注「预估」并说明假设。

### 13. 分层预算 + chargeback + 成本异常告警

部门 → 团队 → 个人的**预算树**,按项目 / 部门出账单分摊(chargeback),成本突增自动告警。

- **复用点**:现有 per-key 配额机制向上扩展为分层预算;建立在 ⑧ 项目维度上;告警经 ④ 飞书通道推送。

## 主线 3 · 多租户与自助

> 底座是 ⑧(见「横切件」):本主线的项目化、自助化都建立在项目维度之上。

### 5. Web 页面生成个人 key 时同步生成接入配置文档

在管理页面(`/ui`)创建 / 生成个人 API key 后,**同步生成该用户的专属接入配置文档**(base URL、key、各客户端接入步骤),可一键下载 / 复制,免去管理员再手工跑脚本发手册。

- **现状**:个人手册目前由命令行脚本 `scripts/auth2api-admin.sh` 产出到 `out/$username.md`,Web 端创建 key 后没有对应文档。
- **目标**:把手册模板能力搬进 Web——创建 key 的响应里即时生成文档(含 `ANTHROPIC_AUTH_TOKEN` 等最新接入方式),供管理员直接发给成员。
- **复用点**:复用 `auth2api-admin.sh` 现有的手册模板内容与结构。
- **注意**:key 仅在创建那一刻明文可见(后端只存 hash),文档须在创建响应中即时生成并提示用户立即保存;文档含明文 key,前端不落库、提示妥善保管。

### 14. 成员自助门户 + 细粒度 RBAC

成员自助看用量、重置自己的 key、申请额度;角色从当前 admin / 普通二元细化为多角色。

- **自助**:减管理员负担,与 ⑤ 接力(⑤ 是开通入口,⑭ 是日常自助)。
- **RBAC**:查看者 / 管理员 / 审计员 / 部门管理员等;权限可挂在 ⑧ 项目维度上。

## 主线 4 · 安全 / 合规 / 内容管控

> 三者都依赖 ⑧ 的项目级开关做差异化:⑦ 决定「服务是否看内容」,看内容才能做 ⑫(管控)与 ⑨(性能)。

### 7. 可选端到端加密 / 明文下的内容分析与安全管控

增加一个**可配置开关**(项目级),决定是否对请求 / 响应内容做端到端加密——这是一个**隐私**与**可观测性、可控性、可优化性**之间的权衡:

- **加密模式(隐私优先)**:服务不接触明文内容,只能做元数据级统计(token 数、模型、耗时、成败),日志不留内容。适合对内容隐私 / 合规要求高的场景。
- **明文模式(可观测优先)**:服务可见请求 / 响应内容,从而能:
  - **内容分析与优化**:prompt 模式分析、缓存命中优化、按内容路由 / 模型选择、高频问题聚类等;
  - **内容安全审计与管控**:敏感信息 / 数据泄露检测、违规内容拦截、合规留痕、按策略阻断请求。
- **衔接现状**:现有请求日志已支持 `error-detail`(full/snippet/off)+ `redact` 脱敏,可作为明文模式审计的基础;加密模式需让日志 / 统计自动降级为仅元数据。
- **注意**:默认值需斟酌(团队内网场景可倾向明文+审计,对外 / 合规场景倾向加密);开关状态应对用户透明(让调用方知道内容是否被服务读取);两种模式都不应把原始凭据写入日志。

### 12. Guardrails + PII / 密钥脱敏(项目级)

在转发层做输入 / 输出双向的内容管控,作为 ⑦「明文模式」最先落地的能力。

- **能力**:prompt 注入 / 越狱检测、敏感内容拦截;PII 与密钥脱敏(身份证 / 手机号 / 代码中的 secret 等)。
- **驱动**:2026 EU AI Act 高风险义务 + OWASP LLM Top 10 使之成为对外 / 合规场景刚需。
- **复用点**:现有日志 `redact` 能力可推广到转发层;策略按 ⑧ 项目配置。

### 9. 语义缓存(项目级开启)

对**重复性高**的项目(FAQ / 客服 / 文档问答)在网关侧做语义缓存:prompt 转 embedding,按相似度命中历史响应则**完全不调上游**(省整次调用 + 近 0 延迟)。

- **为什么必须项目级**:对编程代理(Claude Code)**不适用**——每次请求上下文都不同(命中率低)、且代码答案要求精确(误命中危害大)。因此**默认关**,仅对问答 / 文档类项目按需开启,正是 ⑧ 项目级开关的典型用例。
- **与 Anthropic prompt 缓存的区别**:后者是上游侧前缀**精确**匹配、只省重复 input token、仍调上游;语义缓存是网关侧**模糊**匹配整个请求、命中则不调上游、省 input+output+延迟,但有误命中风险(阈值需调优)。
- **实现要点**:项目配置 `semantic-cache: { enabled, threshold, ttl }`;需 embedding 来源 + 向量存储。

## 主线 5 · 可观测与质量

> ④ 的「分析侧」(日/周/月/年聚合)也归属本主线,见「横切件」。

### 15. OpenTelemetry / Prometheus 导出

暴露 metrics 端点 + OTel trace,接入团队现有 Grafana / Datadog;提供延迟分解(TTFT、tok/s)、慢请求排行等。

### 16. prompt 版本管理 + eval

沉淀团队内「好用的 prompt」并做版本管理 / A/B;对响应打分与回归测试,衡量换模型 / 换账号后的质量变化。

## 依赖关系(实现顺序的硬约束)

```
⑧ 项目底座 ──→ ⑦ 加密 / ⑨ 语义缓存 / ⑫ Guardrails / ⑬ 分层预算   (这些都要按项目配置)
pricing 校准 ──→ ⑥ 节省展示 / ⑬ 预算成本估算
① API 兜底 ──→ ⑱ 批量(兜底内) / 跨模型降级
④ 飞书通道 ──→ 承载 ⑥ 省钱周报、⑬ 预算告警、容量告警的推送
⑤ 建 key 文档 ──→ ⑭ 自助门户(开通入口 → 日常自助)
```

## 推进建议(归纳为 3 阶段)

| 阶段 | 选哪几条 | 为什么 |
|---|---|---|
| **近期 · 打地基 + 强叙事** | pricing 校准 → **⑥**、**⑧** 项目底座、**⑩** 熔断+亲和、**①** API 兜底 | ⑥ 立刻强化省钱叙事;⑧ 是后续一堆功能的前提;⑩ 是调度强项的自然延伸;① 补可用性 |
| **中期 · 治理 + 合规 + 扩供给** | **⑪** 智能路由、**⑬** 预算/chargeback、**⑫** Guardrails/PII、**②** 国内/自部署、**⑭** 自助门户、**④** 飞书 | 治理与合规成型,供给变广,管理负担下放 |
| **远期 · 深化 + 规模化** | **③** 多模态、**⑨** 语义缓存、**⑰** HA、**⑮⑯** 可观测/eval、**⑱** 批量 | 能力深化与规模化运维 |
